# Technical Data Model — Bakery Orders

**Project:** Bakery Orders
**Phase:** Sprint 0 — Architecture Definition
**Status:** Draft — Pending Approval
**Version:** 1.0

---

## 1. Purpose

This document translates the accepted domain model into the initial PostgreSQL relational design.

It defines:

- Tables.
- Relationships.
- Primary and foreign keys.
- Important constraints.
- Initial indexes.
- Snapshot strategy.
- Quantity representation.
- Audit representation.
- Data ownership.
- Expected mutation boundaries.

This document guides the first database migration.

Exact SQL remains implementation work and must be developed through migrations and tests.

---

# 2. General Database Conventions

## Naming

PostgreSQL identifiers use:

```text
snake_case
```

Examples:

```text
business_memberships
requested_quantity
created_at
```

Frontend TypeScript remains:

```text
camelCase
```

Mapping may be handled explicitly where necessary.

---

## Primary Keys

Application entities use UUID primary keys.

Preferred generation:

```text
gen_random_uuid()
```

Authentication-linked Profile IDs reuse the Supabase Auth user UUID.

---

## Timestamps

Persisted operational timestamps use:

```text
timestamptz
```

Database timestamps represent an absolute moment in time.

Display timezone conversion belongs to the presentation layer.

Trusted operational timestamps should normally be generated by PostgreSQL rather than accepted from the browser.

---

## Quantities

Product quantities use exact PostgreSQL numeric values.

Initial target:

```text
numeric(12,3)
```

This supports:

```text
1
12
0.500
1250.750
```

Floating-point types must not be used for quantities requiring exact business validation.

Each Product defines a `quantity_step`.

Examples:

```text
UNIT → 1
TRAY → 1
KG   → 0.100
```

Exact real-world values remain configurable through catalog data.

---

The following stable concepts may use PostgreSQL enums.

## app_role

```text

```

## order_status


# 5. profiles

Application profile associated with Supabase Auth.

```text
profiles
────────────────────────────────────
id                uuid PK
display_name      text NOT NULL
role              app_role NOT NULL
active            boolean NOT NULL
created_at        timestamptz NOT NULL
updated_at        timestamptz NOT NULL
```

## Relationships

```text
profiles.id
    → auth.users.id
```

The application must preserve audit references.

Deleting application users as an ordinary operation is not supported.

Deactivation is preferred.

## Constraints

Conceptually:

```text
display_name must not be blank
active defaults to true
```

Roles cannot be self-assigned by normal users.

---

# 6. businesses

Represents an external establishment.

```text
businesses
────────────────────────────────────
id                  uuid PK
name                text NOT NULL
contact_name        text NULL
contact_phone       text NULL
delivery_address    text NULL
notes               text NULL
active              boolean NOT NULL
created_at          timestamptz NOT NULL
updated_at          timestamptz NOT NULL
```

## Notes

Only information with an operational business purpose should be collected.

`delivery_address` represents the default MVP destination.

Future multi-address support must introduce a dedicated model instead of overloading this column.

## Rules

```text
name cannot be blank
active defaults to true
```

Business records are deactivated rather than physically removed during normal operation.

---

# 7. business_memberships

Associates authorized CUSTOMER users with establishments.

```text
business_memberships
────────────────────────────────────
id             uuid PK
user_id        uuid NOT NULL FK
business_id    uuid NOT NULL FK
active         boolean NOT NULL
created_at     timestamptz NOT NULL
updated_at     timestamptz NOT NULL
```

## Foreign Keys

```text
user_id
    → profiles.id

business_id
    → businesses.id
```

## Unique Constraint

```text
UNIQUE (user_id, business_id)
```

The same user/business relationship must not be duplicated.

A disabled membership remains historically identifiable.

# 8. categories

Represents product categories.

```text
categories
────────────────────────────────────
id             uuid PK
name           text NOT NULL
description    text NULL
active         boolean NOT NULL
display_order  integer NOT NULL
created_at     timestamptz NOT NULL
updated_at     timestamptz NOT NULL
```

## Initial Rules

```text
name cannot be blank
display_order >= 0
active defaults to true
```

A case-insensitive uniqueness strategy for category names should be evaluated in the first migration.

# 9. products

Represents catalog products.

```text
products
────────────────────────────────────
id                       uuid PK
category_id              uuid NOT NULL FK
name                     text NOT NULL
description              text NULL
unit_code                text NOT NULL
quantity_step            numeric(12,3) NOT NULL
image_path               text NULL
active                   boolean NOT NULL
available                boolean NOT NULL
availability_updated_at  timestamptz NULL
availability_updated_by  uuid NULL FK
created_at               timestamptz NOT NULL
updated_at               timestamptz NOT NULL
```

## Foreign Keys

```text
category_id
    → categories.id

availability_updated_by
    → profiles.id
```

## Constraints

Conceptually:

```text
name is not blank
unit_code is not blank
quantity_step > 0
```

An administratively inactive product must not be considered available for new orders.

## Availability

`active` means:

> Is this product administratively part of the current catalog?

`available` means:

> Can this product currently be ordered?

These concepts must remain separate.

## Relationships

```text

```

# 11. Order Number

`id` is the technical UUID identifier.

`order_number` is a human-friendly operational identifier.

Example:

```text
Order #1832
```

The exact formatting displayed in the UI may differ.

Order lookup and authorization must never rely solely on knowing an order number.

---

# 12. Idempotency

Order creation requires an idempotency key.

Initial uniqueness scope:

```text
UNIQUE (
    created_by_user_id,
    idempotency_key
)
```

If the same creation request is repeated unintentionally with the same key, another order must not be created.

A new intentional order uses a new key.

---

# 13. Order Address Snapshot

The current default business delivery address may change over time.

Therefore a confirmed order may preserve:

```text
delivery_address_snapshot
```

This prevents later changes to the Business record from altering the historical destination of an existing order.

If the real business process demonstrates that address snapshots are unnecessary, this decision may be revised before implementation.

---

# 14. Lifecycle Metadata

Lifecycle timestamps and actors exist to make current operational state easy to query.

Examples:

```text
started_at
started_by_user_id

ready_at
ready_by_user_id
```

They do not replace OrderEvent.

Order stores current state.

OrderEvent stores historical transitions.

---

# 15. Cancellation Integrity

A cancelled order must preserve:

```text
cancelled_at
cancelled_by_user_id
cancellation_reason
```

Cancellation reason must be non-empty when an order is cancelled.

The exact SQL consistency constraint may combine:

- CHECK constraints.
- Controlled RPC transitions.

Direct arbitrary status updates are prohibited.

---

# 16. order_items

Represents confirmed product lines.

```text
order_items
──────────────────────────────────────────
id                      uuid PK
order_id                uuid NOT NULL FK
product_id              uuid NOT NULL FK

product_name_snapshot   text NOT NULL
unit_code_snapshot      text NOT NULL
quantity_step_snapshot  numeric(12,3) NOT NULL

requested_quantity      numeric(12,3) NOT NULL
prepared_quantity       numeric(12,3) NOT NULL
unavailable_quantity    numeric(12,3) NOT NULL

created_at              timestamptz NOT NULL
updated_at              timestamptz NOT NULL
```

## Foreign Keys

```text
order_id
    → orders.id

product_id
    → products.id
```

Catalog products referenced by historical orders must not be physically deleted through ordinary application behavior.

---

# 17. Order Item Constraints

Required database invariants:

```text
requested_quantity > 0

prepared_quantity >= 0

unavailable_quantity >= 0

prepared_quantity + unavailable_quantity
    <= requested_quantity
```

Defaults:

```text
prepared_quantity = 0
unavailable_quantity = 0
```

`remaining_quantity` is derived:

```text
requested_quantity
- prepared_quantity
- unavailable_quantity
```

It should not initially be stored as an independent mutable column.

---

# 18. Quantity Step

Order submission must respect the product's `quantity_step`.

Example:

```text
quantity_step = 1
```

Valid:

```text
1
2
15
```

Invalid:

```text
1.5
```

Example:

```text
quantity_step = 0.100
```

Valid:

```text
0.500
1.200
```

Validation occurs at multiple levels.

The exact PostgreSQL enforcement mechanism will be implemented and tested carefully because decimal step validation must avoid floating-point arithmetic.

---

# 19. Product Snapshots

OrderItem stores:

```text
product_name_snapshot
unit_code_snapshot
quantity_step_snapshot
```

Historical orders must not depend entirely on mutable catalog data.

Example:

A product may later change from:

```text
Traditional Croissant
```

to:

```text
Butter Croissant
```

An older order still preserves the original requested information.

---

# 20. order_events

Represents append-oriented order audit history.

```text
order_events
──────────────────────────────────────────
id                uuid PK
order_id          uuid NOT NULL FK
order_item_id     uuid NULL FK
actor_user_id     uuid NULL FK

event_type        text NOT NULL
reason            text NULL

previous_value    jsonb NULL
new_value         jsonb NULL
metadata          jsonb NOT NULL

occurred_at       timestamptz NOT NULL
```

## Relationships

```text
order_id
    → orders.id

order_item_id
    → order_items.id

actor_user_id
    → profiles.id
```

`actor_user_id` may be nullable for legitimate system-generated events.

---

# 21. Event Types

Initial conceptual values:

```text
ORDER_CREATED
PREPARATION_STARTED
QUANTITY_PREPARED
QUANTITY_UNAVAILABLE
ORDER_READY
ORDER_DISPATCHED
ORDER_DELIVERED
ORDER_CANCELLED
```

`event_type` initially remains textual rather than a PostgreSQL enum because audit event vocabulary is expected to evolve.

Validation is still required.

---

# 22. JSONB Usage

JSONB is permitted for event context.

Example:

```json
{
  "quantity": 10,
  "unit": "UNIT"
}
```

JSONB must not replace normal relational modeling.

Do not store complete Orders or Products as arbitrary JSON blobs.

Use JSONB only for event-specific auxiliary information whose structure may legitimately differ between event types.

---

# 23. Event Integrity

OrderEvent should be append-oriented.

Normal users must not:

- Arbitrarily update events.
- Delete events.
- Provide arbitrary actor identities.
- Provide trusted timestamps.

Trusted RPC operations create events.

---

# 24. Current State vs Historical State

The database intentionally keeps both.

Example:

```text
orders.status = READY
```

represents current state.

Meanwhile:

```text
ORDER_CREATED
PREPARATION_STARTED
QUANTITY_PREPARED
ORDER_READY
```

inside `order_events` represents history.

OrderEvent is not event sourcing.

Current operational state remains explicitly persisted.

---

# 25. Fulfillment Condition

Initial design does not persist:

```text
fulfillment_status
```

It is derived from OrderItem quantities.

## COMPLETE

```text
remaining = 0
unavailable = 0
prepared = requested
```

## PARTIAL

```text
remaining = 0
prepared > 0
unavailable > 0
```

## UNAVAILABLE

```text
remaining = 0
prepared = 0
unavailable = requested
```

This avoids maintaining redundant state that could become inconsistent.

Persistence may be reconsidered if query performance eventually justifies it.

# 26. Initial Index Strategy

Indexes should follow actual query requirements.

Initial candidates:

## business_memberships

```text
(user_id, active)
(business_id, active)
```

## products

```text
(category_id)
(active, available)
```

## orders

```text
(business_id, created_at DESC)
(status, requested_delivery_at)
(requested_delivery_at)
(created_at DESC)
```

## order_items

```text
(order_id)
(product_id)
```

## order_events

```text
(order_id, occurred_at)
(order_item_id, occurred_at)
```

Indexes must not be added speculatively without query value.

# 27. Delete Strategy

Normal operational deletion is intentionally restricted.

| Entity | Normal strategy |
|---|---|
| Profile | Deactivate |
| Business | Deactivate |
| BusinessMembership | Deactivate |
| Category | Deactivate |
| Product | Deactivate |
| Order | Never delete |
| OrderItem | Never delete after confirmation |
| OrderEvent | Never delete through normal operations |

Development/test environments may reset data through controlled tooling.

---

# 28. Initial Mutation Boundaries

Direct client mutation is not permitted for critical order tables.

Conceptually:

```text
orders
order_items
order_events
```

must be modified through controlled database operations.

Expected RPC commands:

```text
create_order
start_order
record_prepared_quantity
record_unavailable_quantity
mark_order_ready
dispatch_order
confirm_order_delivery
cancel_order
```

Product availability should also use a controlled operation for KITCHEN so KITCHEN does not gain permission to modify arbitrary Product fields.

---

# 29. RLS Ownership Model

Conceptually:

## CUSTOMER

Can read:

```text
orders belonging to an active authorized business membership
corresponding order_items
corresponding order_events intended for customer visibility
```

Can perform business commands only through authorized RPC operations.

## KITCHEN

Can read bakery operational orders.

Can perform approved production commands.

Cannot perform managerial catalog or establishment administration.

## MANAGER

Can read bakery operational and administrative information.

Can perform approved administrative operations.

Detailed policies belong to `docs/architecture/security.md`.

`order_events` may be added when the UI requires event-stream synchronization.

Realtime exposure must always respect authorization requirements.

```text
products.image_path
```

```text
products/{product_id}/main.webp
```

# 32. Migration Strategy

Initial migration work should be divided by dependency.

Suggested order:

```text
1. enums / shared helpers
2. profiles
3. businesses
4. business_memberships
5. categories
6. products
7. orders
8. order_items
9. order_events
10. indexes
11. grants
12. RLS
13. RPC functions
14. Realtime configuration
```

Whether these become one initial migration or several cohesive migrations will be decided during implementation.

Correctness and reviewability are more important than minimizing migration file count.


# 36. Data Model Acceptance Criteria

Before the first remote deployment:

- All tables exist through migrations.
- Critical foreign keys are defined.
- Critical CHECK constraints are tested.
- RLS exists and is tested.
- Critical RPC operations are tested.
- Cross-business data access is rejected.
- Duplicate order submission is prevented.
- Invalid quantity states are impossible.
- Invalid lifecycle transitions are rejected.
- Audit events are generated consistently.

The database is not considered complete merely because tables can successfully store valid data.

It must also reject invalid and unauthorized states.
